# Configuration and Secrets

## Profiles

| Profile | Database | JWT key | Purpose |
| --- | --- | --- | --- |
| none / prod | DB_URL, DB_USER and DB_PASSWORD required | private JWT_SECRET required | secure default / deployment |
| dev | explicit local PostgreSQL defaults may be used | development-only key unless overridden | local development only |
| test | H2 and synthetic credentials from test resources | test-only key | automated tests, not packaged in the JAR |

`prod` combined with `dev` or `test` is rejected. A BeanFactoryPostProcessor validates
secrets before datasource/Flyway initialization. Missing values, known placeholders,
the old public JWT defaults, development/test signing keys in production and the
old database password in production fail startup. JWT keys require at least 32 UTF-8
bytes; use a cryptographically random value rather than a memorable phrase. Failure
messages name the setting but do not echo its value. JwtProperties also redacts its
toString representation and validates issuer and positive token lifetimes.

## Required Deployment Variables

| Variable | Required | Description |
| --- | --- | --- |
| SPRING_PROFILES_ACTIVE | use prod | No active profile is equally strict; never deploy with dev/test |
| DB_URL | yes, except Compose supplies it | PostgreSQL JDBC URL |
| DB_USER | yes | Database login; Compose also initializes POSTGRES_USER |
| DB_PASSWORD | yes | Private database password; Compose also initializes POSTGRES_PASSWORD |
| JWT_SECRET | yes | Private random signing key, at least 32 UTF-8 bytes |
| DB_NAME | Compose default: fasswerk | Initial PostgreSQL database name |
| BOOTSTRAP_ADMIN_EMAIL | optional, together with password | First administrator's email |
| BOOTSTRAP_ADMIN_PASSWORD | optional, together with email | At least 16 characters, at most 72 UTF-8 bytes for BCrypt |

The root `.env.example` is a Compose template. Its empty secrets deliberately fail
`docker compose config` until explicitly supplied. Compose runs the backend as prod
and shares the chosen DB credentials with PostgreSQL. No secret is generated by the
application for production. Supply secrets through your deployment environment or a
private, ignored `.env` file; do not commit them or put them into CLI arguments.

Flyway's Maven plugin now uses DB_URL/DB_USER/DB_PASSWORD from the process environment
(or explicit `-Dflyway.*` configuration); it has no separate credential defaults.
Production database changes continue to use Flyway migrations only.

## Local Development

From `backend`, run `./scripts/run-local.sh`. On first use it creates `.env` with
private filesystem permissions from `.env.example` and exits so it can be reviewed.
On the next invocation it sources that file, selects dev, checks the configured
port/database connection and runs Spring Boot. The dev database defaults are the
existing local fasswerk database/user/password, only in the explicit dev configuration.
The script rejects any profile selection other than dev. Direct Maven starts can use
`./mvnw spring-boot:run -Dspring-boot.run.profiles=dev`.

`FASSWERK_ENV_FILE` can point the local script at another private environment file.
Environment files are trusted shell input, must only be writable by their owner and
must quote spaces/shell metacharacters. They are not loaded by Spring automatically.
The previously tracked local `backend/.env` has been retained on disk but removed from
the Git index. Remove old placeholder JWT values from that local file to use the dev
profile key, or replace them with a private key. Never activate dev just to bypass a
production validation error.

## Initial Administrator

Fresh databases no longer expose the published seed logins after migrations finish.
Provide both BOOTSTRAP_ADMIN_EMAIL and BOOTSTRAP_ADMIN_PASSWORD for the first start,
using a new email address and a privately chosen password. The startup runner creates
an active ADMIN with a BCrypt hash only if no active administrator exists. If that
same active admin already exists, subsequent startup does not change its password.
Existing disabled accounts or STAFF accounts cannot be overwritten/promoted by this
mechanism. Remove both bootstrap variables after successful provisioning. Start a
single instance for initial provisioning, then scale out.

Deployments with an existing active administrator do not need bootstrap variables.
Additional user management is not introduced by this refactoring phase.

## Upgrade From Legacy Defaults

Migration V21 selectively finds the two published legacy password hashes, removes
refresh tokens for those users, deactivates their accounts and replaces the hashes
with a non-login marker. Already changed passwords/accounts are preserved. Historical
V1-V20 files are unchanged. Operators must provide a new private administrator via the
bootstrap when all previous administrators still used legacy seed credentials.

Rotate a previously public/reused JWT_SECRET before this upgrade. V21 removes refresh
sessions but does not revoke every already issued access JWT; the existing filter
uses JWT roles without re-reading account activity. Rotating the signing key rejects
previously signed access and refresh JWTs. This deliberate session invalidation is
part of moving away from the published defaults; notify users before deployment.

The old tracked environment file remains in Git history. Removing it from the index
does not revoke its values or erase old clones. Any value that was ever used outside
local development must be rotated by the operator. No live credentials, external
accounts, existing databases or Git history were modified by this phase.

## Verification

```bash
cd backend
./mvnw clean verify
cd ../frontend
npm ci
npm run lint
npm run build
npm run test:e2e:critical
```

`SecretConfigurationTest` loads real YAML/profile configuration and checks missing,
invalid and valid credentials, profile conflicts, development settings and bootstrap
requirements. `AdminBootstrapTest` checks opt-in, BCrypt storage and protection of
existing accounts. `LegacySeedMigrationTest` checks the selective transition and
refresh-session removal with H2; this does not replace PostgreSQL integration tests.
The phase report records additional isolated PostgreSQL and packaged-JAR smoke checks.
Playwright uses one worker locally and in CI because its shared Next dev server
compiles routes on demand; test timeouts and assertions are unchanged.
